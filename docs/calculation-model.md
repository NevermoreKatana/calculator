# Математическая модель Ganache Calculator

Документ описывает, что именно вычисляет приложение, на каких данных, и — что
не менее важно — **чего оно не вычисляет и почему**.

Три уровня данных строго разделены и не смешиваются:

| Уровень | Что это | Статус в приложении |
|---|---|---|
| 1. Рецептурный | Вода %, сахара %, сухая масса %, жиры %, какао % | **Точный расчёт** из состава ингредиентов |
| 2. Физико-химический | Активность воды `a_w` | **Только измеренное значение**; расчётной модели нет |
| 3. Практический | Теоретический срок годности | **Только эмпирические контрольные точки** + документированная интерполяция |

Правильная цепочка:

```
Ингредиенты → Рецептурный состав → Water / Sugar / Dry Matter
   → a_w (только измеренный или валидированной моделью)
   → Микробиологические зоны риска
   → Эмпирические контрольные точки срока
   → Теоретическая оценка
```

Чего приложение **не делает**: `Water % → выдуманный a_w → выдуманный срок`.

## 1. Источник модели: разбор Excel

Исходник — `docs/source/формирование ганаша программа.xlsx`
(SHA-256 `fca5f328f62e4b911a879429fd4b4a65d5cd2846b0a0aa2b444d74407b487f65`),
листы `Database`, `calculator`, `page print`.

### 1.1 Лист `Database`

113 ингредиентов, строки 6–118. Значения хранятся как доли (0.35), приложение
хранит проценты (35).

| Колонка | Заголовок в Excel | Поле модели |
|---|---|---|
| A | ингредиенты | `name` |
| B | сахара | `sugarPercentage` |
| C | жиры → раст. жиры и молочные | `fatPercentage` (все жиры **кроме** масла какао) |
| D | жиры → масло какао | `cocoaButterPercentage` |
| E | сухое → молоко | `milkSolidsPercentage` |
| F | сухие → какао | `cocoaSolidsPercentage` |
| G | прочие → сухие | `otherSolidsPercentage` |
| H | вода | `waterPercentage` |
| I | цена | `pricePerKg` |
| J | сладость | `sweetness` |

Сопоставление колонок **проверено**, а не угадано: лист `calculator` хранит
индексы VLOOKUP в ячейках `D1:J1` (значения 2…8), и, например, `calculator!F5`
вызывает `VLOOKUP($C5, Database!$A:$I, D$1=2)` → `Database!B` = сахара.

### 1.2 Лист `calculator`

Строки 5–29 — до 25 позиций рецепта.

```
D  количество, г
E  = D / $D$30                       доля от общего веса
F..N = VLOOKUP(имя, Database, компонент) × E     доля компонента от всего рецепта
D30 = SUM(D5:D29)                    общий вес
```

Блок «о рецепте», строки 36–41 (он же источник круговой диаграммы):

```
D36 общие жиры          = G30 + H30     (прочие жиры + масло какао)
D37 сахара              = F30
D38 обш какао           = J30           (только сухие какао, без масла какао)
D39 общ молочные сухие  = I30
D40 прочие сухие        = K30
D41 вода                = L30
```

Заголовок `G4 = "28-32"` — технологический ориентир по общей доле жиров, 28–32 %.
Приложение показывает его как ориентир и подсвечивает попадание в диапазон.

### 1.3 Лист `page print`

Модуль масштабирования:

```
G31 = 400                            целевой вес партии
A2  = G31 / calculator!D30           коэффициент масштабирования
G12 = $A$2 × calculator!D5           вес позиции после масштабирования
H12 = G12 / $G$31                    процент
```

Это в точности логика из §38 ТЗ, и она перенесена без изменений.

## 2. Повреждённые формулы Excel и что с ними сделано

Ни одна повреждённая формула не перенесена в приложение. Каждая разобрана.

| Место | Что сломано | Решение |
|---|---|---|
| `calculator!A3:A207` | Вся колонка `=#REF!` | Удалена. Остаток удалённого листа, на расчёт не влияла |
| `calculator!F7:N7` | `VLOOKUP(#REF!, …)` — строка «sugar inverted», 0.8 г, давала **0** по всем компонентам | Восстановлено: строка ссылается на свой ингредиент |
| `calculator!F8:N8` | `VLOOKUP($C7, …)` — сдвиг на строку: позиция «glucose» подставляла состав **инвертного сахара** | Восстановлено: строка ссылается на свой ингредиент |
| `calculator!K1` | Пустая ячейка → индекс VLOOKUP = 0 → колонка `M` (цена) **всегда 0** | Восстановлен индекс 9 → `Database!I` |
| `calculator!M5:M29` | Цена умножалась на **долю** веса, что не согласуется с `M31 = (M30/D30)×1000` и `D33 = M30/D32` | Восстановлено размерно корректно: `цена/кг × г / 1000`. См. §2.1 |
| `page print!B14` | `=calculator!#REF!` | Удалена |
| `page print!G34` | `#DIV/0!` — деление на количество штук = 0 | Защищено: возвращает «—», а не ошибку |

### 2.1 Неоднозначность: колонка цены

Excel считал `M5 = цена × E5`, где `E5` — доля веса. Тогда `M30` — средневзвешенная
цена за кг, и `M31 = (M30/D30)×1000` теряет размерность.

Но `L31` подписана «за кг», а `D33 = M30 / D32` подписана «цена за шт». Обе
подписи имеют смысл **только** если `M30` — полная стоимость партии.

**Вывод:** замысел однозначен (`M30` = стоимость партии), реализация в Excel —
нет. Приложение реализует замысел:

```
costValue  = pricePerKg × weightGrams / 1000
totalCost  = Σ costValue
costPerKg  = totalCost / totalWeightGrams × 1000
```

Это единственное место, где восстановлен *замысел*, а не буква формулы;
отмечено здесь явно.

### 2.2 Что восстановить не удалось

* Позиция `calculator!C8 = "glucose"` (3 г). В `Database` такого ингредиента
  нет — есть `sugar glucose 40DE` и `sugar glucose 60DE` с разной сладостью
  (0.45 и 0.65) при одинаковом составе. Какой имелся в виду — определить
  невозможно. **Не угадано.**
* Позиция `calculator!D13 = 35` г с пустой ячейкой ингредиента `C13`.
  35 г неизвестно чего — 5.8 % сохранённого рецепта. **Не угадано.**

Обе позиции исключены из тестов паритета и описаны в
`tests/excel-parity.test.ts`.

## 3. Качество данных `Database`

Семь компонентов должны давать 100 % массы ингредиента. В источнике это не так.

| Наблюдение | Количество строк |
|---|---|
| Сумма ≈ 100 % (99.5–100.5) | 46 |
| Сумма < 99.5 % | 64 |
| Сумма > 100.5 % — физически невозможно | 3 |

Строки с суммой > 100 %: `fruit puree кокс capfruit` (124.3 %),
`fruit puree мандарин` (106.0 %), `fruit puree banana` (109.0 %).

**Решение: ничего не нормализуется.** Данные импортируются как есть, а разница
показывается отдельной величиной «не учтено»:

```
unaccountedGrams = weightGrams − Σ(компоненты в граммах)
```

Причина: нормализация — это молчаливое изобретение данных. Если состав пюре
описан на 94 %, приложение обязано сказать «6 % не описано», а не растянуть
известные компоненты до 100 % и выдать догадку за факт. Отрицательное значение
«не учтено» прямо указывает на противоречие в источнике.

## 4. Базовые формулы

Все реализованы в `src/lib/calculator/`, вне React-компонентов.

```
totalWeightGrams      = Σ ingredient.weightGrams

ingredientPercentage  = weightGrams / totalWeightGrams × 100

waterGrams            = Σ (weightGrams × waterPercentage / 100)
sugarGrams            = Σ (weightGrams × sugarPercentage / 100)
fatGrams              = Σ (weightGrams × fatPercentage / 100)
cocoaButterGrams      = Σ (weightGrams × cocoaButterPercentage / 100)
milkSolidsGrams       = Σ (weightGrams × milkSolidsPercentage / 100)
cocoaSolidsGrams      = Σ (weightGrams × cocoaSolidsPercentage / 100)
otherSolidsGrams      = Σ (weightGrams × otherSolidsPercentage / 100)

waterPercentage       = waterGrams / totalWeightGrams × 100
sugarPercentage       = sugarGrams / totalWeightGrams × 100

totalFatGrams         = fatGrams + cocoaButterGrams          (Excel D36)

dryMatterGrams        = totalWeightGrams − waterGrams
dryMatterPercentage   = dryMatterGrams / totalWeightGrams × 100

accountedSolidsGrams  = сумма шести объявленных сухих компонентов
unaccountedGrams      = dryMatterGrams − accountedSolidsGrams

sugarWaterRatio       = sugarGrams / waterGrams
```

### 4.1 Сухая масса ≠ сумма сухих компонентов

Различие, которого в Excel не было:

* `dryMatterGrams` — всё, что не вода (определение из ТЗ §7);
* `accountedSolidsGrams` — сумма шести *объявленных* сухих компонентов.

Они совпадают только когда состав ингредиента описан на 100 %. Разница — это
«не учтено», и она видна в интерфейсе.

### 4.2 Масштабирование

```
scaleFactor = targetTotalWeightGrams / baseTotalWeightGrams
newWeight   = oldWeight × scaleFactor
```

Целевой вес определяется в порядке: `pieceCount × pieceWeightGrams` →
явный `targetTotalWeightGrams` → без масштабирования.

Проценты инвариантны относительно масштабирования — это проверяется тестом.

### 4.3 Округление

Промежуточные значения **не округляются**. Округление только при отображении,
через `formatGrams` / `formatPercent` / `formatRatio` в
`src/lib/calculator/numeric.ts`.

### 4.4 Отсутствие `NaN` / `Infinity`

Любое деление проходит через `safeDivide`, который возвращает `null` вместо
не-конечного числа. `null` отображается как «—». Тест обходит весь объект
результата и проверяет конечность каждого числового поля.

Отдельный случай: `sugarWaterRatio` при нулевой воде — это `null`, а не
`Infinity`, и интерфейс пишет «не определено».

## 5. Активность воды (`a_w`)

### 5.1 Вода в рецептуре ≠ `a_w`

Это разные физические величины. 17.5 % воды **не означает** `a_w = 0.825` или
любое другое автоматически выводимое значение. `a_w` зависит от количества
воды, сухих веществ, **типа** сахаров, растворённых веществ, жиров, солей,
температуры, структуры продукта и взаимодействия компонентов.

Интерфейс всегда показывает обе величины рядом и никогда не подменяет одну
другой.

### 5.2 Почему `a_w` не рассчитывается

Известные уравнения для кондитерских изделий (Norrish, Money–Born, Grover)
требуют **мольной** концентрации каждого растворённого вещества. Импортированная
база даёт для этого недостаточно данных:

| Требуется уравнением | Есть в базе |
|---|---|
| Раздельно сахароза / глюкоза / фруктоза / инвертный сироп / сорбит | Одна суммарная колонка «сахара» |
| Молярные массы растворённых веществ | Нет |
| Содержание солей (NaCl) | Нет колонки; строка `sel` вообще без состава |
| Разделение «прочих сухих» на растворимые и нерастворимые | Нет |
| Температура продукта | Нет |

Это не осторожность — уравнение **невозможно инстанцировать** на этих данных.
Поэтому `FutureScientificAwModel` ничего не считает и возвращает список
недостающих величин.

### 5.3 Архитектура моделей

`src/lib/water-activity/models.ts`, цепочка по приоритету:

1. **`MeasuredAwModel`** — значение с прибора, введённое пользователем.
   Единственная модель, которая сейчас может вернуть число. Приоритет над всем.
2. **`ReferenceAwModel`** — подбор по таблице измеренных `a_w` эталонных
   рецептур. Таблица `REFERENCE_AW_MEASUREMENTS` **пуста**: предоставленные
   контрольные точки содержат воду, сахара и дни, но ни одного измерения `a_w`.
   Заполнение таблицы активирует модель без изменения остального кода.
3. **`FutureScientificAwModel`** — слот для валидированной модели. Не реализован
   (см. 5.2).

Источник значения показывается всегда: «Измеренное значение» / «Справочное
измерение» / «Расчётная модель» / «Нет данных».

### 5.4 Микробиологические зоны

Транскрипция исходного графика, `src/lib/water-activity/zones.ts`:

| Диапазон | Зона | id |
|---|---|---|
| `a_w < 0.60` | Нет роста | `no_growth` |
| `0.60–0.65` | Осмофильные дрожжи | `osmophilic_yeasts` |
| `0.65–0.75` | Ксерофильные плесени | `xerophilic_molds` |
| `0.75–0.80` | Большинство галофильных бактерий | `halophilic_bacteria` |
| `0.80–0.87` | Большинство плесеней; патогенных бактерий нет | `most_molds` |
| `> 0.86` | Возможен рост *Staphylococcus aureus* | `staphylococcus_aureus_possible` |
| `0.87–0.90` | Дрожжи, плесени-продуценты микотоксинов | `yeasts_and_mycotoxin_molds` |
| `0.91–0.95` | Кокки, лактобациллы, *Salmonella* | `broad_bacterial_growth_risk` |
| `> 0.95` | Большинство бактерий | `most_bacteria` |

**Пересечение `0.80–0.87` и `> 0.86` воспроизведено намеренно.** Это не ошибка
интерфейса: на исходном графике зоны действительно пересекаются, потому что
описывают два разных биологических факта об одном участке шкалы. Классификатор
возвращает **все** подходящие зоны как список флагов:

```ts
{ waterActivity: 0.865,
  risks: ['most_molds', 'staphylococcus_aureus_possible'] }
```

«Текущая зона» для отображения — зона с наибольшей нижней границей, то есть
самый серьёзный перейдённый порог.

#### Границы: два решения, которые пришлось принять явно

* **Порог 0.86 включающий (`a_w ≥ 0.86`).** График подписан «> 0.86», но
  worked-example в ТЗ (§21) показывает `a_w = 0.86` именно как зону
  *S. aureus*. Для флага пищевой безопасности консервативное прочтение —
  срабатывать **на** пороге, а не объявлять его безопасным.
* **Порог 0.95 строгий (`a_w > 0.95`).** Здесь 0.95 — явная закрывающая граница
  предыдущего диапазона `0.91–0.95`, поэтому она остаётся за ним.

#### Разрыв в исходных данных

Между `0.87–0.90` и `0.91–0.95` есть промежуток: при `0.90 < a_w < 0.91`
подходит только открытая зона `> 0.86`. Разрыв присутствует в источнике и
**сохранён** — он не закрыт интерполяцией.

### 5.5 График не предсказывает срок

График `a_w → микроорганизмы` **не является** графиком `a_w → дни хранения`.
Он показывает потенциальную микробиологическую активность. Срок оценивается
отдельным модулем, и `a_w` в его арифметике не участвует (см. 6.4).

## 6. Теоретическая оценка срока годности

### 6.1 Эмпирические контрольные точки

Единственные данные, на которых строится оценка:

| # | Вода | Сахара | Срок, дней |
|---|---|---|---|
| 1 | 17.5 % | 35 % | 90 |
| 2 | 18.6 % | 32 % | 58–63 |
| 3 | 20.0 % | 30–32 % | 38–44 |

Это **наблюдения** для конкретного продукта и процесса — не физический закон,
не гарантированный срок и не формула.

### 6.2 Формулы срока годности нет

В предоставленных материалах нет математической зависимости, связывающей
воду %, сахара % и сухую массу со сроком хранения. Псевдонаучная формула ради
получения числа не создаётся. Вместо неё — **reference-based estimation**.

### 6.3 Алгоритм

`src/lib/shelf-life/estimate.ts`:

1. Совпадение с контрольной точкой (вода ±0.15 п.п., сахара в диапазоне точки
   ±0.5 п.п.) → возвращается наблюдённое значение,
   метод `reference_point_match`.
2. Вода вне `17.5–20 %` → **отказ**. Экстраполяция не выполняется.
3. Вода между двумя соседними точками → интерполяция (см. 6.4).
4. Иначе → `insufficient_data` с указанием причины.

### 6.4 Интерполяция — и почему она одномерная

Три контрольные точки **не разбросаны** по плоскости (вода, сахара) — они лежат
на одной монотонной траектории: вода растёт 17.5 → 18.6 → 20.0, сахара падают
35 → 32 → 30–32, срок падает 90 → 58–63 → 38–44.

Три точки на одной траектории не задают двумерную поверхность: любая
подогнанная плоскость была бы произвольным выбором из бесконечного множества
проходящих через эти данные. Поэтому:

* интерполяция ведётся **только по воде**;
* содержание сахаров **проверяется** на соответствие траектории между теми же
  двумя точками (допуск ±2.0 п.п.);
* если сахара сошли с траектории — рецепт вне области наблюдений, и выдаётся
  «Нет достаточной эмпирической информации», а не число.

```
t        = (water − w_lower) / (w_upper − w_lower)
daysMin  = daysMin_lower + t × (daysMin_upper − daysMin_lower)
daysMax  = daysMax_lower + t × (daysMax_upper − daysMax_lower)
```

Метод всегда показывается пользователю:
**«Интерполяция между эмпирическими контрольными точками»**. Приложение не
создаёт видимости точной научной формулы.

### 6.5 `a_w` не влияет на срок

`a_w` принимается и отображается, но **не участвует** в арифметике срока:
контрольные точки не содержат измерений `a_w`, а график `a_w` — не график дней.
Это проверяется тестом: один и тот же рецепт даёт одинаковое число дней с
измеренным `a_w` и без него.

### 6.6 Влияние сухой массы — качественно

Исходные материалы утверждают: «фактор свободной воды также зависит от сухой
массы, чем её больше, тем меньше свободной воды». Это **качественное**
наблюдение, а не формула. Приложение показывает его как текст и **не**
вычисляет из него `a_w`.

### 6.7 Соотношение сахар / вода

```
sugarWaterRatio = sugarGrams / waterGrams      → «2.00 : 1»
```

Вспомогательный аналитический параметр. **Не** доказанная формула срока
годности. При нулевой воде — `null`, а не `Infinity`.

## 7. Ограничения модели

1. **Теоретическая оценка не является гарантированным сроком годности.**
   Фактический срок зависит от технологии, температуры, упаковки,
   герметичности, pH, санитарных условий, активности воды, состава, условий
   хранения, типа шоколадной оболочки, миграции влаги и других факторов.
   Подтверждение требует реальных испытаний стабильности и микробиологических
   исследований.
2. Область применимости оценки — вода 17.5–20 %, сахара 30–35 %. Вне её
   приложение отказывается считать.
3. Контрольные точки получены для одного продукта и процесса; перенос на другую
   рецептуру, оболочку или технологию не обоснован.
4. `a_w` не рассчитывается. Без прибора он остаётся неизвестным.
5. 64 из 113 ингредиентов описаны не полностью, 3 — противоречиво. Точность
   расчёта состава ограничена качеством исходных данных, и приложение это
   показывает, а не скрывает.
6. Open Food Facts даёт только сахара и жиры; воду по панели питательной
   ценности вычислить нельзя, и она **не** доинтерполируется вычитанием.
7. Сладость (`sweetness`) перенесена из Excel как относительный индекс без
   документированной шкалы; используется только для сравнения рецептов.
